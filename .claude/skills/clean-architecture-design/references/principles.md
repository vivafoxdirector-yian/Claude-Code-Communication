# Clean Architecture 핵심 원칙

출처: Robert C. Martin, *Clean Architecture* (assets/reference 의 PDF가 원천 자료).

---

## 0. 아키텍처의 목표

- 시스템을 만드는 데 드는 **인력 비용을 최소화**하고, 수명 동안 **변경 비용을 낮추는 것**.
- "동작하는 코드"는 최소 요건일 뿐. 좋은 구조는 **선택지(options)를 열어둔 채** 결정을 늦춘다.
- 세부사항(DB, 웹, 프레임워크, UI)은 **정책이 아니라 디테일**이다. 정책(업무 규칙)이 디테일을 모르게 한다.

---

## 1. SOLID — 클래스/모듈 수준 원칙

| 원칙 | 한 줄 정의 | 위반 신호 | 처방 |
|------|-----------|-----------|------|
| **SRP** 단일 책임 | 모듈은 **하나의 액터(변경 이유)** 에게만 책임진다 | 한 클래스를 서로 다른 이유로 여러 팀이 고친다 | 책임별로 분리, 변경 이유로 클래스를 가른다 |
| **OCP** 개방-폐쇄 | 확장에는 열려 있고 수정에는 닫혀 있다 | 새 요구마다 기존 코드 수정 | 추상화 + 다형성으로 확장점 제공 |
| **LSP** 리스코프 치환 | 하위 타입은 상위 타입을 **대체 가능** 해야 한다 | `if (type == X)` 분기, 정사각형/직사각형 문제 | 계약(사전/사후조건) 준수, 잘못된 상속 제거 |
| **ISP** 인터페이스 분리 | 쓰지 않는 것에 의존하게 만들지 마라 | 거대한 인터페이스의 일부만 구현 | 클라이언트별로 인터페이스 분할 |
| **DIP** 의존성 역전 | **추상에 의존**하고 구체에 의존하지 마라 | 고수준 모듈이 구체 클래스를 직접 `new` | 인터페이스 추출, 팩토리/주입으로 구체화 격리 |

DIP 실천: 변동성이 큰 구체 클래스를 직접 참조하지 않는다 → 인터페이스를 두고, 생성은 Abstract Factory 또는 DI로 경계 바깥에서 한다.

## 2. 컴포넌트 응집 (Component Cohesion) — 무엇을 한 컴포넌트에 넣는가

세 원칙은 서로 긴장 관계(Tension Diagram)이며 균형이 핵심이다.

- **REP** (Reuse/Release Equivalence): 재사용 단위 = 릴리스 단위. 함께 릴리스·버전 관리되는 것을 묶는다.
- **CCP** (Common Closure): **같은 이유로 같은 시점에 바뀌는** 클래스를 한 컴포넌트에 모은다. (SRP의 컴포넌트 버전)
- **CRP** (Common Reuse): **함께 쓰이지 않는** 클래스를 한 컴포넌트에 두지 마라. (ISP의 컴포넌트 버전)

→ 초기엔 CCP(개발 편의), 성숙하면 REP/CRP(재사용) 쪽으로 무게가 이동.

---

## 3. 컴포넌트 결합 (Component Coupling) — 컴포넌트 간 의존

- **ADP** (Acyclic Dependencies): 컴포넌트 의존 그래프에 **순환이 없어야** 한다. 순환 발견 시 DIP로 끊거나 새 컴포넌트로 분리.
- **SDP** (Stable Dependencies): **안정성이 높은 방향**으로 의존하라. 자주 바뀌는 컴포넌트가 안정된 컴포넌트에 의존해야 한다. (불안정 → 안정)
- **SAP** (Stable Abstractions): 안정적인 컴포넌트일수록 **추상적**이어야 한다(인터페이스/추상 클래스 중심). 그래야 안정성과 확장성을 동시에 얻는다.

지표: I = 나가는 의존/(들어오는+나가는). A = 추상 클래스 비율. 이상적으로 I + A ≈ 1 (Main Sequence).

---

## 4. 의존성 규칙 (The Dependency Rule) — 가장 중요한 규칙

**소스 코드 의존성은 항상 안쪽(고수준 정책)을 향한다.** 안쪽 원은 바깥 원의 어떤 것도 알지 못한다.

동심원(안 → 밖):
1. **Entities** — 전사적 핵심 업무 규칙 (가장 안정·고수준)
2. **Use Cases** — 애플리케이션 고유 업무 규칙 (애플리케이션 흐름)
3. **Interface Adapters** — Controllers / Presenters / Gateways (데이터 형식 변환)
4. **Frameworks & Drivers** — DB, 웹, UI, 외부 도구 (가장 바깥, 디테일)

규칙:
- 안쪽은 바깥의 이름(클래스/함수/변수)을 절대 언급하지 않는다.
- 경계를 넘는 데이터는 **단순한 구조체/DTO**. 바깥 프레임워크의 엔티티를 안으로 넘기지 않는다.
- 제어 흐름과 소스 의존성이 반대일 때 **DIP로 역전**시킨다.

---

## 5. 경계 (Boundaries) — 선을 어디에 긋는가

- 변동성이 큰 것(DB 종류, 웹 프레임워크, UI)과 안정적인 업무 규칙 사이에 경계를 긋는다.
- **세부사항은 플러그인**으로: DB는 디테일, 웹은 디테일, 프레임워크는 디테일. 업무 규칙이 이들에 의존하지 않게 한다.
- 경계 횡단은 **인터페이스 + Humble Object 패턴**으로. (테스트 어려운 부분을 얇게, 로직을 테스트 가능하게 분리)
- 경계는 비싸므로 **완전 경계 / 부분 경계(One-dimensional, Facade)** 중 비용 대비 필요만큼.

## 6. 패키징 전략 (The Missing Chapter)

- **Package by Layer** (controller/service/repository) — 단순하나 기능 변경 시 여러 패키지 수정. 비추.
- **Package by Feature** — 기능 단위로 묶음. 응집도↑.
- **Ports and Adapters** — 도메인(inside)과 인프라(outside)를 포트/어댑터로 분리. 의존성 규칙과 잘 맞음.
- **Package by Component** — 컴포넌트를 배포 단위로, 잘 정의된 인터페이스로 노출. 권장.
- 핵심: **조직(가시성)보다 캡슐화**. public 남발은 컴파일러가 의존 규칙을 강제하지 못하게 한다.

---

## 7. "디테일은 디테일이다"

- **The Database Is a Detail** — DB는 저장 메커니즘일 뿐. 업무 규칙은 SQL/스키마를 몰라야 한다.
- **The Web Is a Detail** — 웹은 IO 채널. UseCase가 HTTP를 몰라야 한다.
- **Frameworks Are Details** — 프레임워크와 결혼하지 마라(비대칭 관계). 핵심 로직을 프레임워크에 종속시키지 않는다.
- **Test Boundary** — 테스트도 시스템 컴포넌트. 테스트 가능하게 설계(Design for Testability)하면 자연히 좋은 구조가 된다.
