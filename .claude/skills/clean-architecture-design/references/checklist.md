# Clean Architecture 설계/검토 체크리스트

설계 또는 코드 구조 검토 시 아래 항목을 점검한다. 위반 시 심각도와 함께 처방을 제시한다.

## A. 의존성 규칙 (최우선)
- [ ] 소스 의존성이 항상 안쪽(업무 규칙)을 향하는가?
- [ ] Entities/UseCase가 DB·웹·프레임워크·UI의 타입을 import 하지 않는가?
- [ ] 경계를 넘는 데이터가 단순 DTO/구조체인가? (ORM 엔티티·프레임워크 객체 누수 없음)
- [ ] 제어 흐름과 반대 방향의 의존은 DIP로 역전되어 있는가?

## B. SOLID
- [ ] **SRP**: 각 모듈의 변경 이유(액터)가 하나인가?
- [ ] **OCP**: 새 요구를 기존 코드 수정 없이 확장으로 수용할 수 있는가?
- [ ] **LSP**: 하위 타입이 상위 타입 자리에서 깨지지 않는가? 타입 검사 분기가 없는가?
- [ ] **ISP**: 클라이언트가 쓰지 않는 메서드에 의존하지 않는가?
- [ ] **DIP**: 고수준 모듈이 구체 클래스 대신 추상에 의존하는가? 생성이 경계 밖(팩토리/DI)에 있는가?

## C. 컴포넌트
- [ ] **순환 의존성(ADP)** 이 없는가? (있으면 DIP로 단절 또는 컴포넌트 분리)
- [ ] **안정 의존(SDP)**: 자주 바뀌는 컴포넌트가 안정 컴포넌트에 의존하는가? (역방향 아님)
- [ ] **안정 추상(SAP)**: 안정적인 컴포넌트가 추상(인터페이스)으로 노출되는가?
- [ ] **응집(CCP/CRP)**: 함께 바뀌는 것은 모여 있고, 함께 안 쓰이는 것은 분리되어 있는가?

## D. 경계 & 디테일
- [ ] DB가 플러그인(디테일)으로 격리되어 교체 가능한가?
- [ ] 웹/UI가 IO 채널로만 취급되는가? UseCase가 HTTP를 모르는가?
- [ ] 프레임워크 종속이 핵심 로직까지 침투하지 않았는가?
- [ ] 테스트 가능하게 설계되었는가? (Humble Object로 IO/뷰 분리)

## E. 패키징
- [ ] 패키지가 Layer가 아닌 Feature/Component 기준으로 묶여 있는가?
- [ ] 가시성(public) 남용 없이 캡슐화로 의존을 강제하는가?

## 구조 진단 결과
