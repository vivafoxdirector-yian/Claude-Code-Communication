# Clean Architecture Design

Robert C. Martin의 *Clean Architecture* 원칙에 따라 시스템/모듈 구조를 설계하거나 검토한다. 특정 언어가 아닌 **구조와 의존성 방향**에 초점을 둔다.

## 핵심 전제

> 좋은 아키텍처는 **결정을 최대한 늦추고**, 세부사항(DB·웹·프레임워크)을 **플러그인**으로 격리하여 변경 비용을 낮춘다.
> 아키텍처의 목적은 "동작하게 만드는 것"이 아니라 "오래도록 싸게 바꿀 수 있게 하는 것"이다.

## Workflow

### 1. 설계/검토 대상 파악
- 신규 설계: 도메인(업무 규칙), 외부 의존(DB/웹/프레임워크/외부 API)을 먼저 식별한다.
- 기존 구조 검토: 의존성 방향과 계층 경계를 그려보고 위반을 찾는다.

### 2. 원칙 적용
상세 원칙은 [references/principles.md](references/principles.md) 참조.

설계 시 항상 던지는 질문:
- **의존성 규칙**: 소스 코드 의존성이 항상 안쪽(고수준 정책)을 향하는가? 업무 규칙이 DB/UI/프레임워크를 모르는가?
- **SOLID**: SRP(변경 이유 하나), OCP(확장 개방/수정 폐쇄), LSP(치환 가능), ISP(필요한 것만), DIP(추상에 의존).
- **컴포넌트 응집**: REP/CCP/CRP 균형. 함께 바뀌는 것을 함께 둔다.
- **컴포넌트 결합**: 순환 의존 금지(ADP), 안정성 방향 의존(SDP), 안정적인 것은 추상적이게(SAP).
- **경계**: 변동성이 큰 세부사항(DB/웹/UI)을 경계 바깥 플러그인으로 밀어낸다.

### 3. 구조 진단 / 제안
[references/checklist.md](references/checklist.md)의 체크리스트로 점검하고, 위반 항목에 대해:
- **무엇이** 어떤 원칙을 위반했는지
- **왜** 문제인지(변경 비용/테스트 어려움/재사용 저해)
- **어떻게** 고칠지(의존성 역전·인터페이스 추출·계층 분리 등 구체적 리팩토링)

심각도 기준:
- **CRITICAL**: 의존성 규칙 역전(업무 규칙이 DB/프레임워크에 직접 의존), 순환 의존성
- **MAJOR**: SRP 위반(다중 변경 이유), DIP 미적용(구체 클래스 직접 의존), 계층 누수
- **MINOR**: 컴포넌트 응집 불균형, 경계 불명확
- **SUGGESTION**: 패키징 전략 개선, 플러그인화 여지

### 4. 결과 정리
구조 다이어그램(텍스트/머메이드)과 함께 의존성 방향을 명시한다. 한국어로 작성한다.
