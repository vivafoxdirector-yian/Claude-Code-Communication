# GoF 23 디자인 패턴 카탈로그

출처: Gamma, Helm, Johnson, Vlissides, *Design Patterns: Elements of Reusable Object-Oriented Software* (GoF).
파이썬 관점은 [python-notes.md](python-notes.md) 참조.

각 항목: **의도 / 언제 / 오용 신호**.

## 생성 패턴 (Creational) — "객체를 어떻게 만드는가"

### Factory Method
- **의도**: 객체 생성을 서브클래스에 위임. 어떤 클래스를 인스턴스화할지 서브클래스가 결정.
- **언제**: 생성할 구체 타입이 런타임/하위 클래스에 따라 달라질 때.
- **오용 신호**: 타입이 하나뿐인데 팩토리 계층부터 만든다.

### Abstract Factory
- **의도**: 관련된 객체 **군(family)** 을 구체 클래스 노출 없이 생성.
- **언제**: 일관된 제품군(예: OS별 위젯 세트)을 통째로 교체해야 할 때.
- **오용 신호**: 제품군이 하나뿐. → Factory Method로 충분.

### Builder
- **의도**: 복잡한 객체의 **생성 과정**을 표현과 분리, 단계적으로 조립.
- **언제**: 생성자 인자가 많거나(텔레스코핑), 선택적 조합이 다양할 때.
- **오용 신호**: 필드 2~3개에 빌더. → 키워드 인자/dataclass로 충분(파이썬).

### Prototype
- **의도**: 기존 인스턴스를 **복제(clone)** 해 새 객체 생성.
- **언제**: 생성 비용이 크거나, 런타임 구성으로 만든 객체를 복제할 때.
- **오용 신호**: 단순 객체. → `copy.deepcopy`로 충분(파이썬).

### Singleton
- **의도**: 인스턴스를 **하나만** 보장하고 전역 접근점 제공.
- **언제**: 진짜 단 하나여야 하는 자원(설정·커넥션 풀 등).
- **오용 신호**: 사실상 전역 변수/숨은 의존성 → 테스트 어려움. 남용 주의. (파이썬: 모듈 자체가 싱글톤, 또는 Borg/monostate)

## 구조 패턴 (Structural) — "객체를 어떻게 조합하는가"

### Adapter
- **의도**: 호환 안 되는 인터페이스를 클라이언트가 기대하는 형태로 변환.
- **언제**: 기존/외부 클래스를 수정 없이 다른 인터페이스에 맞출 때.
- **오용 신호**: 내가 만든 코드를 굳이 어댑터로 감쌈. → 처음부터 맞는 인터페이스로.

### Bridge
- **의도**: 추상과 구현을 **분리해 독립적으로 확장**.
- **언제**: 추상×구현의 조합 폭발을 막고 싶을 때(예: Shape × Renderer).
- **오용 신호**: 구현이 하나뿐인데 분리.

### Composite
- **의도**: 개별 객체와 복합 객체를 **동일하게** 다룸(트리 구조).
- **언제**: 부분-전체 계층(파일시스템·UI 트리·메뉴).
- **오용 신호**: 계층이 없고 평면 컬렉션이면 불필요.

### Decorator
- **의도**: 객체에 **동적으로 책임 추가**(상속 대신 조합/래핑).
- **언제**: 기능 조합이 다양하고 런타임에 쌓고 싶을 때.
- **주의**: 파이썬의 `@decorator` 문법(함수 데코레이터)과 **다른 개념**. 혼동 금지.

### Facade
- **의도**: 복잡한 서브시스템에 **단순한 통합 진입점** 제공.
- **언제**: 하위 시스템 사용법이 복잡해 클라이언트를 보호하고 싶을 때.
- **오용 신호**: 단순 호출을 의미 없이 한 겹 더 감쌈.

### Flyweight
- **의도**: 다수의 유사 객체가 **공유 상태(intrinsic)** 를 공유해 메모리 절약.
- **언제**: 동일/유사 객체가 대량 생성될 때(문자 글리프 등).
- **오용 신호**: 객체 수가 적으면 복잡도만 증가. (파이썬: `__slots__`, 인터닝, 캐싱이 먼저)

### Proxy
- **의도**: 대상 객체에 대한 **대리/접근 제어**(지연 로딩·캐싱·권한·원격).
- **언제**: 실제 객체 접근 전후로 제어가 필요할 때.
- **오용 신호**: 부가 동작 없는 빈 위임.

## 행위 패턴 (Behavioral) — "책임/알고리즘을 어떻게 분배하는가"

### Chain of Responsibility
- **의도**: 요청을 처리할 객체를 **체인**으로 연결, 처리 가능한 핸들러까지 전달.
- **언제**: 미들웨어·이벤트 처리·검증 단계 파이프라인.
- **오용 신호**: 핸들러가 항상 하나면 불필요.

### Command
- **의도**: 요청을 **객체로 캡슐화**(실행 취소/큐잉/로깅 가능).
- **언제**: 작업의 실행/취소/이력이 필요할 때.
- **파이썬**: 일급 함수·클로저·`functools.partial`로 흔히 대체.

### Iterator
- **의도**: 내부 표현 노출 없이 **순차 접근** 제공.
- **파이썬**: `__iter__`/`__next__`, 제너레이터로 **언어에 내장** — 대개 직접 구현 불필요.

### Mediator
- **의도**: 객체 간 **직접 참조를 줄이고** 중재자를 통해 상호작용(결합도↓).
- **언제**: 다대다 상호작용이 얽힐 때(UI 컴포넌트 조정).
- **오용 신호**: 중재자가 거대해져 God Object가 됨.

### Memento
- **의도**: 캡슐화를 깨지 않고 객체 상태를 **저장/복원**(undo).
- **언제**: 스냅샷·체크포인트가 필요할 때.

### Observer
- **의도**: 한 객체 상태 변화 시 **의존 객체들에 자동 통지**(publish/subscribe).
- **언제**: 이벤트·반응형 갱신(모델→뷰).
- **오용 신호**: 통지 흐름이 추적 불가능해질 정도로 남발.

### State
- **의도**: 내부 **상태에 따라 행위를 바꿈**(상태별 클래스로 분기 제거).
- **언제**: 상태 전이가 많고 `if/elif` 분기가 비대해질 때.
- **오용 신호**: 상태 2개뿐이면 단순 분기로 충분.

### Strategy
- **의도**: 교체 가능한 **알고리즘군을 캡슐화**, 런타임에 선택.
- **언제**: 같은 작업의 여러 알고리즘(정렬·요금 계산·검증).
- **파이썬**: 별도 클래스 계층 없이 **함수를 인자로 전달**하는 게 관용적.

### Template Method
- **의도**: 알고리즘 **골격을 상위 클래스**에, 가변 단계는 서브클래스에.
- **언제**: 전체 흐름은 같고 일부 단계만 다를 때.
- **파이썬**: 부분 적용(partial)·고차 함수로도 표현 가능.

### Visitor
- **의도**: 객체 구조를 바꾸지 않고 **새 연산을 추가**(연산을 객체로 분리).
- **언제**: 안정된 구조에 연산이 자주 추가될 때(AST 처리).
- **오용 신호**: 구조가 자주 바뀌면 오히려 부담(double dispatch 비용).

### Interpreter
- **의도**: 간단한 언어의 **문법을 클래스로 표현**하고 해석.
- **언제**: 작은 DSL·표현식 평가.
- **오용 신호**: 복잡 문법엔 부적합 → 파서 도구 사용.

## GoF 외 실무 패턴 (Beyond GoF)

GoF 23개에는 없지만 현업에서 자주 쓰이는 패턴. 다수는 **GoF 패턴의 조합 + 아키텍처 원칙(특히 DIP)** 의 실무적 형태다. (구조/경계 차원은 `clean-architecture-design` 스킬과 연계)

### SPI (Service Provider Interface) / Plugin
- **의도**: **확장 지점을 인터페이스로 열어두고**, 구현체(provider)를 런타임에 **발견(discover)하거나 교체**한다. 프레임워크가 내 구현을 호출(IoC, Hollywood Principle: "Don't call us, we'll call you").
- **API vs SPI**:
  - **API** = 호출자가 *사용하는* 인터페이스 (내가 호출한다)
  - **SPI** = 제공자가 *구현하는* 인터페이스 (프레임워크가 내 구현을 호출한다)
- **언제**: 드라이버/백엔드/플러그인을 코어 수정 없이 추가·교체해야 할 때.
- **메커니즘 예**:
  - Java: `java.util.ServiceLoader` + `META-INF/services` (JDBC `Driver`, SLF4J 바인딩)
  - Python: `importlib.metadata.entry_points` (setuptools entry points)
- **관계**: **DIP를 런타임 discovery로 구현한 형태**. 내부적으로 Strategy(구현 교체) + Abstract Factory(구현 생성) + Plugin 아키텍처가 결합.
- **오용 신호**: 구현체가 영원히 하나뿐인데 SPI 인프라(서비스 로더·등록 메커니즘)부터 구축. → 단순 DI/직접 의존으로 충분.

### Dependency Injection (DI) / IoC Container
- **의도**: 객체가 **의존성을 스스로 생성하지 않고 외부에서 주입**받는다. 생성 책임과 사용 책임 분리.
- **방식**: 생성자 주입(권장) / 세터 주입 / 인터페이스 주입.
- **언제**: 결합도를 낮추고 테스트(목 주입)를 쉽게 하고 싶을 때. SPI/Strategy 실현의 토대.
- **관계**: DIP의 가장 흔한 실천 수단. (Abstract Factory가 "무엇을 만들지", DI는 "누가 넣어줄지")
- **오용 신호**: 소규모인데 무거운 IoC 컨테이너 도입. 파이썬은 대개 명시적 생성자 주입으로 충분.

### Repository
- **의도**: 도메인과 데이터 저장소 사이에 **컬렉션처럼 보이는 추상 계층**을 두어 영속성 세부를 감춘다.
- **언제**: 도메인 로직을 DB/ORM에서 분리하고 싶을 때(Clean Architecture의 경계와 직결).
- **관계**: DIP + Adapter. 인터페이스는 도메인 계층, 구현은 인프라 계층(Ports & Adapters).
- **오용 신호**: ORM 위에 의미 없는 1:1 위임 래퍼만 추가(추상화 가치 없음).

### Unit of Work
- **의도**: 하나의 비즈니스 트랜잭션 동안 일어난 객체 변경을 **모아서 한 번에 커밋/롤백**.
- **언제**: 여러 Repository 변경을 원자적으로 묶어야 할 때. 흔히 Repository와 짝.

### Null Object
- **의도**: `None` 대신 **기본 동작을 가진 객체**를 반환해 분기(`if x is None`)를 제거하고 다형성 유지.
- **언제**: "없음" 케이스에도 동일 인터페이스로 다루고 싶을 때. (Clean Code in Python Ch.9에서 다룸)

### DTO (Data Transfer Object)
- **의도**: 계층/경계를 넘는 **단순 데이터 묶음**. 동작 없이 데이터만.
- **관계**: Clean Architecture에서 "경계를 넘는 데이터는 단순 구조체" 규칙의 실체. (파이썬: `@dataclass`, `pydantic`)

## 패턴 선택 빠른 가이드

| 문제 유형 | 후보 패턴 |
|-----------|-----------|
| 생성이 복잡/조건부 | Factory Method, Abstract Factory, Builder |
| 인터페이스 불일치 | Adapter |
| 기능을 동적으로 추가 | Decorator, Proxy |
| 복잡한 서브시스템 단순화 | Facade |
| 트리/부분-전체 | Composite |
| 알고리즘 교체 | Strategy, Template Method |
| 상태별 행위 분기 | State |
| 이벤트 통지 | Observer |
| 작업 캡슐화/undo | Command, Memento |
| 처리 단계 파이프라인 | Chain of Responsibility |
| 플러그인/드라이버 확장 | **SPI / Plugin** |
| 의존성 결합 낮추기 | **Dependency Injection** |
| 영속성 분리 | **Repository / Unit of Work** |
| 계층 간 데이터 전달 | **DTO** |
