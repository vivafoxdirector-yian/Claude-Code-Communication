# 제품 문서

**이 문서는 규약 설명이다. 실제 자리는 제품 저장소(`org.workdir`)에 만든다** —
`./aiorg scaffold` 가 만들어 준다.

PO 가 만든다. 조직이 바뀌어도 파일로 남으므로, 기획 조직에서 개발 조직으로
넘어갈 때 인계물이 되는 곳이다.

| 경로 | 내용 | 누가 쓰나 |
|---|---|---|
| `research/<주제>.md` | **경쟁 조사 결과.** 사실만, 출처 필수. 여럿이 함께 보탠다 | PO 또는 프리세일즈 |
| `specs/<기능>.md` | **채택된 요구사항 정의서.** 개발팀이 이걸 보고 만든다 | PO |
| `backlog.md` | 아직 때가 아닌 제안들 | PO |

## 경쟁 조사 — 중복은 막지 않고, 대조하게 한다

경쟁 정보는 PO 와 프리세일즈가 **둘 다 필요로 한다.** 목적이 다를 뿐이다.

| | 무엇을 보나 | 무엇에 쓰나 |
|---|---|---|
| PO | 기능 **갭** — 우리에게 없는 것 | 무엇을 만들지 정한다 |
| 프리세일즈 | **차별점** — 우리가 나은 것 | 고객에게 어떻게 설명할지 정한다 |

사실은 `research/` 에 모으고, 해석은 각자 자기 산출물에 쓴다
(PO → `specs/`·제안, 프리세일즈 → `docs/sales/경쟁비교.md`).

### 왜 "한 벌만" 이 아닌가

한 사람의 조사를 다른 사람이 검증 없이 받아쓰면 **단일 실패점**이 된다.
구성원은 전부 Claude 세션이고, 근거 없이 그럴듯하게 채울 수 있다.
그 한 번의 착오가 조직의 사실이 되고, 그 위에 요구사항이 쌓이고, 개발자가 그걸 만든다.

실제로 그런 일이 있었다 — 출처가 하나도 없는 7개 제품 비교표를 근거로
요구사항 정의서가 작성됐고 아무도 잡지 못했다.

사람 조직에서 두 사람이 따로 조사해 같은 결론에 이르면 신뢰도가 올라간다.
**LLM 조직에서는 그 가치가 더 크다.** 그래서 중복을 금지하지 않는다.

### 다만 — 중복 자체가 시너지는 아니다

시너지는 각자 한 부씩 갖고 있어서가 아니라 **맞춰보기 때문에** 난다.
따로 만들어 놓고 아무도 안 읽으면 낭비이고, 더 나쁜 건 나중에 누가 하나만 읽는 것이다.

그래서 규칙은 이것이다:

> **먼저 것이 있으면 출발점으로 삼되 그대로 믿지 않는다.
> 출처를 확인하고, 내 관점에서 빠진 것을 같은 파일에 보탠다.
> 어긋나는 지점을 찾으면 맞춰주지 말고 양쪽을 다 남긴 뒤 올린다.**

어긋남은 실패가 아니라 **발견**이다. 이걸 문책하면 다음부터 조용히 먼저 것에
맞춰버리고 검증 기능이 사라진다.

```markdown
- Slite 가격: Standard $8/user/mo
  출처: https://slite.com/pricing (2026-09-04 po-market 확인)
  ⚠ 불일치 — presales 조사에는 $6.99. 확인 시점 차이로 추정. 미해결.
```

억지로 하나로 합치지 않는다. 미해결 표시가 붙은 항목은 그것에 기대는 결정을 내릴 때
누구든 조심하게 된다. 다만 **고객에게 나가는 숫자**(가격 등)는 미해결로 둘 수 없다 —
확정될 때까지 자료에서 뺀다.

## 요구사항 정의서에 반드시 들어갈 것

`specs/` 의 문서는 개발자가 그대로 보고 만드는 것이다. 애매하면 짐작해서 만들고,
그건 대개 틀린다. 다섯 가지를 빠뜨리지 않는다.

- **목적** — 왜 만드는가 (사용자에게 무엇이 좋아지는가)
- **범위** — 무엇을 만드는가
- **제외 범위** — 무엇은 만들지 않는가 ← 이게 빠지면 범위가 계속 늘어난다
- **동작** — 정상 흐름과 **실패 흐름**. 실패 케이스를 안 적으면 아무도 안 만든다
- **완료 기준** — 무엇이 되면 끝난 것인가 (검증 가능한 문장으로)

근거가 VOC 라면 출처를 적는다 (`docs/voc/raw/` 의 어느 파일인지).
대표 지시라면 "대표 지시" 라고 적는다. 나중에 왜 만들었는지 되짚기 위해서다.
