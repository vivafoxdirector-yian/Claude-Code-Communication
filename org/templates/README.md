# 조직 템플릿

시작점이다. **여기 있는 파일을 직접 고치지 말고 복사해서 쓴다.**

```bash
./aiorg templates                 # 목록
./aiorg new product-team mycorp   # org/mycorp.yaml 로 복사
./aiorg up --org mycorp           # 내 조직으로 띄우기
```

복사해 두면 프레임워크를 갱신해도 당신이 손본 조직도가 덮이지 않는다.
`org/default.yaml` 이라는 이름으로 만들어 두면 `--org` 없이 `./aiorg up` 만으로 뜬다.

그냥 한 번 돌려보는 것이라면 템플릿을 바로 띄워도 된다: `./aiorg up --org solo`

## 무엇이 있나

| 템플릿 | 규모 | 무엇이 다른가 |
|---|---|---|
| `solo` | 2명 / 1세션 | 대표와 실무자 하나. 프레임워크 확인용, 토큰이 가장 적게 든다 |
| `minimal` | 4명 / 1세션 | 대표 → 팀장 → 실무자 2. 3계층의 최소형 |
| `startup` | 5명 / 2세션 | **부서장이 없다.** 전원 대표 직속. 대표가 배정과 검수를 다 한다 |
| `product-team` | 8명 / 5세션 | **표준.** 기획·개발·품질·사업을 모두 갖춘 형태 |
| `two-po` | 8명 / 4세션 | PO 2인이 제품 영역을 나눠 맡는다. 담당 경계의 예시 |
| `quality-first` | 8명 / 3세션 | **개발 2 : 리뷰 2.** 모든 산출물이 리뷰를 거치게 짠 조직 |
| `research` | 5명 / 3세션 | **개발자가 없다.** 산출물이 코드가 아니라 문서. PO 위에 기획팀장 |
| `research-build` | 10명 / 5세션 | `research` 에 개발·품질부를 붙인 것. **기획 멤버 id 가 같아 일이 이어진다** |
| `enterprise` | 14명 / 6세션 | 4계층. 개발 2팀, 기획팀장, 고객군별 프리세일즈 |
| `existing-product` | 8명 / 3세션 | **이미 있는 제품에 붙이는 형태.** `workdir`·`areas` 로 프론트/백엔드 위치를 선언 |

## 고르는 법

- **처음이라면** `solo` 나 `minimal` 로 한 번 굴려보고 감을 잡는다.
- **실제 개발 업무**에는 `product-team` 이 기본이다. 병목이 보이는 부서만 나중에 늘린다.
- **이미 있는 제품을 개선·확장**하려면 `existing-product`. `workdir` 을 제품 저장소로 잡고
  `areas` 에 프론트/백엔드 경로를 적으면, 팀장이 그걸 기준으로 배정한다.
- **정확성이 속도보다 중요**하면(결제, 인증, 마이그레이션) `quality-first`.
- **무엇을 만들지부터 정해야 하면** `research` 로 기획만 돌리고, 정해지면 개발 조직으로 옮긴다.
- `enterprise` 는 **먼저 정말 필요한지 생각해 본다.** 14개 세션이 각자 컨텍스트를 유지하므로
  토큰 소비가 크다. 대개 `product-team` 으로 충분하다.

## 조직을 바꿔야 할 때 — 교체하지 말고 확장한다

`research` 로 기획을 마치고 개발로 넘어가는 경우처럼, 도중에 조직 구성이 바뀔 때가 있다.

**중요한 것 하나: 멤버 id 가 곧 주소다.** 태스크의 담당자도, 수신함 디렉터리 이름도
전부 멤버 id 다. 그래서 조직도를 갈아끼워 id 가 사라지면 **그 사람의 일이 고아가 된다** —
태스크는 `runtime/` 에 남아 있는데 담당자가 조직에 없으니 아무도 하지 않고,
아무에게도 보이지 않는다.

```bash
./aiorg up --org product-team   # research 로 일하다가 갑자기 교체하면
```
```
경고: 이전 조직의 미완료 태스크 1건이 남아 있습니다. 담당자가 새 조직에 없습니다: po-product
      확인: ./aiorg task list --open
      인계: ./aiorg task set --id <태스크id> --assignee <새 담당자>
      종료: ./aiorg task set --id <태스크id> --status cancelled --note "조직 개편으로 종료"

경고: 새 조직에 없는 멤버의 미확인 메시지가 남아 있습니다: po-product(2)
```

`up` 이 잡아서 알려주긴 하지만, 애초에 그럴 일을 만들지 않는 편이 낫다.

### 권장 — 같은 id 를 유지한 채 멤버를 추가한다

```bash
./aiorg down
./aiorg up --org research-build     # 기획부 id 는 그대로, 개발·품질부가 붙는다
```

경고가 뜨지 않고 태스크와 수신함이 그대로 이어진다.
`research` → `research-build` 가 그 예시이고, 직접 만들 때도 원리는 같다:
**남길 사람의 `id` 를 그대로 두고 멤버를 더한다.**

```bash
./aiorg new research mycorp    # 내 조직도로 복사
# org/mycorp.yaml 에 개발부 멤버를 추가한다 (기존 id 는 건드리지 않는다)
./aiorg up --org mycorp
```

### 넘어간 뒤 하는 일

기획 산출물은 `docs/` 에 파일로 남아 있으므로 조직이 바뀌어도 그대로다.

1. 대표가 `docs/product/specs/` 의 요구사항 정의서를 근거로 개발팀장에게 배정한다
2. 개발자가 그 문서를 읽고 만든다
3. 요구사항이 모호하면 개발자가 **담당 PO 에게 직접 질문**한다
   (수평 질문은 조직도 규칙에 걸리지 않는다 — 제한되는 것은 지시와 보고뿐이다)

### 정말 처음부터 다시 시작하려면

이전 조직의 태스크·수신함을 아예 버리고 싶을 때만 쓴다. **되돌릴 수 없다.**

```bash
./aiorg down
./aiorg clean --force   # 메시지 큐, 태스크, 이벤트 로그가 사라진다
./aiorg up --org product-team
```

`clean` 은 무엇을 잃는지 먼저 보여준다(`--force` 없이 실행). `rm -rf runtime` 을
직접 하지 않는다 — 조직이 아직 도는지, 커밋 안 된 작업이 있는지 확인해 주기 때문이다.

`docs/` 의 산출물과 `worktrees/` 의 코드는 지워지지 않는다.

## 고칠 때 알아둘 것

모든 템플릿이 같은 역할 정의(`org/roles/*.md`)를 공유한다. 조직도가 바꾸는 것은
**누가 있고, 누구에게 보고하고, 무엇을 담당하는가** 뿐이다.

- `org.workdir` 이 구성원들이 일하는 곳이다. **안 쓰면 이 저장소가 기본.**
  기존 제품에 붙이려면 그 저장소의 절대경로를 준다 (WSL 형식: `/mnt/c/dev/myapp`).
  경로가 없으면 `up` 이 거부한다 — 조용히 홈 디렉터리에서 일하게 되는 것을 막기 위해서다
- `members[].workdir` 로 멤버마다 시작 위치를 달리 줄 수 있다 (조직 `workdir` 기준 상대경로).
  안 쓰면 조직 `workdir` 을 그대로 쓴다
- `use_skills` 는 **Claude Code 스킬 이름**이다 (`skills` 태그와 다른 것).
  역할에 걸면 그 역할 전원이 물려받고, `brief` 가 각자에게 알려준다.
  스킬 자체는 지정할 설정이 없다 — Claude Code 가 `~/.claude/skills/`(어디서든)와
  `<프로젝트 루트>/.claude/skills/`(그 프로젝트 안)를 알아서 본다.
  단 git 워킹트리나 외부 저장소에서는 이 저장소의 스킬에 닿지 못한다 — `up` 이 경고한다.
  전원이 쓸 스킬은 `~/.claude/skills/` 에 두면 확실하다
- **`org.session_prefix`** 는 tmux 세션 이름의 앞부분이다 (기본 `aiorg`).
  이 저장소를 복사해 프로젝트를 여러 개 동시에 돌린다면 **반드시 다르게 바꾼다** —
  겹치면 나중에 뜬 쪽이 먼저 돌던 조직을 죽인다. `up` 이 그 상황을 감지해 거부한다
- `session` 이 같은 멤버끼리 하나의 tmux 세션(= 부서)으로 묶인다
- `reports_to` 가 보고선이다. 비우면 최상위(사용자가 대화할 상대)
- `skills` 는 `engineer` 에게는 기술 역량, `po`·`presales` 에게는 **담당 영역**이다.
  뒤의 둘은 겹치면 `up` 이 경고한다 (`exclusive_skills: true`)
- `layout` 은 `windows`(멤버당 창 하나, 기본) 또는 `panes`(격자 분할)

검증은 `up` 이 한다 — id 중복, 없는 상급자, 보고선 순환, 미정의 역할은 거부된다.
